## 2. Rules that must not be broken

* **Use the production `.htaccess` profile only.** `npm run build:hostinger` writes the **staging** profile (adds `X-Robots-Tag: noindex, nofollow`, HSTS `max-age=300`) and would hide the live site from Google. Production is produced only with the explicit command in section 3.
* **Back up the current live files before changing anything** (section 4). No backup, no release.
* **Order matters: assets, then pages, then `.htaccess` last, then the sitemap** (section 5). Never delete old files during the release.
* **Do not touch DNS, e-mail settings, the Hostinger plan, WordPress files or databases.** This release only replaces website files in the document root.
* Upload the **contents of `dist/`**, never `site/`, `backend/`, `infra/`, `node_modules/`, `.git/` or `vercel.json`.
* Stop and roll back at the first failed check in section 6 (triggers in section 7). Do not "fix forward" on the live server.

6. Choose a quiet time. Tell whoever answers the phone/WhatsApp that a short check window is happening.

## 5. Release: safely ordered upload

Why the order: pages are cached by browsers for 5 minutes and reference **hashed** CSS/JS files; the new pages use new hashed names, so the new assets must exist **before** the new pages, and the old assets must **stay** so a cached old page is never left unstyled. The `.htaccess` is what makes the exact URLs and the redirects work, so it is switched **after** the pages are in place, and the sitemap advertises the new URLs **last**.

### 5A. Preferred, if Hostinger allows it (atomic switch)

Upload the complete new tree, including the production `.htaccess`, into a **separate folder** that is not the live document root, test it there if you can reach it (rules that use the site root only work when the folder is a document root of its own), and then switch the domain's document root, or rename the folders, so that the new tree becomes the live one in one step. Keep the old folder untouched as the rollback copy. Use this only if the owner has confirmed item 6 in section 1; otherwise use 5B.

### 5B. Standard ordered upload into the live document root

1. **Assets first:** upload `dist/assets/` (all subfolders: css, js, img, fonts). The new hashed CSS/JS files are added next to the old ones; never delete or rename existing files.
2. **Pages:** upload every `dist/*.html` (including `404.html` and `index.html`). New files (the eight newly added pages and the restored articles) can be uploaded in any order.
3. **`.htaccess`:** replace the document-root `.htaccess` with `dist/.htaccess` **as the very next step** (a single file, so the routing switches at once). Do not leave the site between steps 2 and 3 longer than necessary: between them, new pages link to exact URLs that the old rules do not yet serve.
4. **Crawler files:** `sitemap.xml`, then `robots.txt`.
5. Purge any Hostinger page cache/CDN, if section 1 item 5 says one is on.
6. **Straight away run section 6.** Do not walk away.

Do **not** upload `dist/.htaccess` under any other name inside the public folder, and never leave an old `.htaccess` copy lying in the public folder.

## 7. Rollback

**Triggers (any one):** a 5xx or a blank/unstyled site; any failure in 6.1 or 6.2; the header check shows `X-Robots-Tag: noindex`; the WhatsApp form does not open WhatsApp or shows the preview message; e-mail test fails or MX records differ; a page in 6.3 does not return 200.

**Steps, in this order (target: under 15 minutes):**

1. **Restore the routing first:** put back `htaccess.live-original.txt` as `.htaccess` in the document root. This alone ends a site-wide 500 or a wrong redirect.
2. **Restore the pages:** copy the backed-up `*.html` files (and `404.html`, `index.html`) over the live ones.
3. **Restore the crawler files:** the backed-up `sitemap.xml` and `robots.txt`.
4. **Leave the new hashed assets in place** (harmless; the old pages ignore them). Files that exist only in the new release can be removed later, one at a time, by comparing listings with the backup; do not bulk-delete.
5. Purge any cache (if enabled) and **run the "before" checks again** (Appendix A): the output must match `before.txt`. Repeat the header and e-mail checks.
6. Write down what failed (which check, which URL, the response) and stop. Do not retry the release until the cause is found and the fix has been built, verified and reviewed.

Notes:

* Rollback returns the site to the **previous static build**, not to WordPress. Whether an old WordPress copy still exists on the server is unknown (section 1, item 4); returning to WordPress would be a separate decision.
* HSTS (`max-age=31536000`) is already live on this domain; a rollback does not need to change it. **Never lower or remove it during an incident.**
* Keep the backup for at least 30 days.

## Appendix A: read-only URL check script

Save as `check-urls.sh` and run it in Git Bash (or any bash): `BASE=https://sfrmotors.co.uk bash check-urls.sh`. It only sends GET requests and follows no redirects.

```bash
#!/usr/bin/env bash
# Read-only URL check. Expected values are the ones this branch serves.
BASE="${BASE:-https://sfrmotors.co.uk}"
fail=0; n=0
check() { # path, expected status, [expected redirect target path]
  local out code loc
  out=$(curl -s -o /dev/null --max-time 20 -w '%{http_code} %{redirect_url}' "$BASE$1") || { echo "FAIL $1 (curl error)"; fail=$((fail+1)); n=$((n+1)); return; }
  code=${out%% *}; loc=${out#* }; n=$((n+1))
  if [ "$code" = "$2" ] && { [ "$2" != 301 ] || [ "$loc" = "$BASE$3" ]; }; then echo "PASS $1 -> $code $loc"
  else echo "FAIL $1 wanted $2 ${3:-} got $code $loc"; fail=$((fail+1)); fi
}
# 1. The 35 URLs served at their exact URL: 200 with and without the slash; the old .html form makes one 301 to it.
while read -r p; do
  [ -z "$p" ] && continue
  check "$p" 200; check "${p%/}" 200
  f="${p%/}.html"; [ "$p" = "/mobile-tyre-fitting-in-addiewell/" ] && f="/mobile-tyre-fitting-addiewell.html"
```
